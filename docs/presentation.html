Community Pub Management

Hederochel
Shift & Report Platform

A web application for volunteer bartenders and pub administrators — managing shifts, reports, and staff from a single interface. Built in Hebrew, deployed on Vercel, powered by Supabase.

🍺 Bartenders — sign up for shifts, complete reports
🗂️ Managers — schedule shifts, manage users, review reports
Next.js App Router Supabase Auth + DB Vercel Playwright TypeScript Hebrew / RTL
Version 1 Scope

What We're Building

👤 User Management
  • Email/password signup & login
  • Two roles: Bartender & Manager
  • Suspend / unsuspend accounts
  • Delete user accounts
  • Managers change roles & passwords
  • Role-based access control (API + UI)
  • Profile view & edit
📅 Shift Management
  • Managers create / edit / delete shifts
  • Calendar view of all shifts
  • Lifecycle: open → full → running → closed
  • Bartenders sign up & cancel
  • View upcoming & past shifts
  • State-based signup guards
  • Link shifts to reports
📋 Shift Reports
  • Auto-create report on shift start
  • Task checklist from active template
  • Bartenders mark tasks & add notes
  • Report auto-closes when all tasks done
  • Managers view completed reports
  • CRUD task templates
  • Reports read-only after shift closes

Open Gaps & Risks

Items Requiring Attention

⚠ Decision Required — Architecture
TSK-SHF-012/013: Time-based state transitions require a trigger mechanism. Recommended approach: lazy evaluation at API read time (no background job). Alternative: Supabase scheduled function (pg_cron). Decision needed before implementation begins — affects how reports auto-create on shift start.
⚠ Gap — Shift Signup API
TSK-SHF-014 (partial): The shift signup API only blocks signup for closed shifts. It does not block full or running shifts at the API level. The UI prevents it, but the API is bypassable. Fix is small — one condition in the signup handler.
⚠ Gap — Suspended User Enforcement
TSK-SHF-015: Suspended users are blocked from login (Supabase ban_duration) but the shift signup API does not check suspension status. A suspended user with a valid session could sign up for a shift via direct API call.
⚠ Gap — Default Landing Page Redirect
TSK-UI-007: The task remains marked todo in the backlog but may already be partially implemented. Needs verification before the next planning round. If not implemented, role-based redirect after login is missing.
⚠ Gap — Requirements File Staleness
The four REQ-*.md files still reflect stale statuses for implemented features (e.g., REQ-USR-001, REQ-USR-006–008 marked todo but implemented). Task CSVs have been updated; requirement files have not been reconciled.
